# AC Efficiency Bot — AirClimat.pmr

Телеграм-бот: клиент пишет модель кондиционера → бот узнаёт текущую уличную
температуру → просит Claude определить тип кондиционера и оценить падение
КПД обогрева по оцифрованным графикам с klimresh.by.

## Почему так, а не жёсткая формула по бренду

Изначально обсуждалась идея с фиксированным словарём марок/моделей. Но:

- Марок и моделей на рынке — сотни, поддерживать словарь вручную нереально.
- Пользователь прямо попросил: пусть **сам Claude** определяет тип по
  названию модели, без ограничения на конкретных производителей.

Поэтому вся классификация и интерполяция происходит **внутри одного запроса
к Claude** (`system_prompt.py`), а код бота — это просто обвязка:
Telegram ↔ погода ↔ Claude ↔ ответ клиенту.

## Точность цифр

Опорные точки в `system_prompt.py` оцифрованы вручную по скриншотам трёх
графиков с сайта klimresh.by (простой инвертор, зимний инвертор, суперинвертор).
Считывание "на глаз" по клеточкам графика — точность ±5-10 процентных пунктов.
Для дружелюбного бота этого достаточно, для инженерных расчётов — нет.

У "зимнего инвертора" на реальном графике четыре разные кривые в зависимости
от мощности (09K/12K/18K/24K) — в промпте заложены все четыре отдельно.
Если Claude определил тип "зимний инвертор", но не знает мощность модели —
бот дополнительно спросит у клиента мощность (BTU или кВт), прежде чем
считать итоговый процент. Диалог может состоять из нескольких уточнений
подряд (сначала тип, потом мощность) — состояние на этот случай хранится
в `PENDING_CLARIFICATION` вместе с накопленными ответами клиента.

## Настройка

```bash
pip install -r requirements.txt
export TELEGRAM_BOT_TOKEN="токен от @BotFather"
export ANTHROPIC_API_KEY="ключ с console.anthropic.com"
export AC_BOT_LOG_PATH="dialogs.jsonl"   # необязательно, по умолчанию dialogs.jsonl
python bot.py
```

## Выбор города

По умолчанию город **не задан** — при первом сообщении в чате (когда клиент
пишет модель кондиционера) бот сначала спросит "Из какого вы города?", и
только после ответа продолжит расчёт (город нужен, чтобы узнать погоду).
Дальше город запоминается на весь чат и повторно не спрашивается. Найденные
координаты — через бесплатный Geocoding API Open-Meteo (без ключа).

Поменять уже сохранённый город можно в любой момент командой `/city
<название>`, например `/city Тирасполь`.

Привязка города к чату хранится в памяти процесса (`CHAT_CITIES`) — при
перезапуске бота сбрасывается, и бот снова спросит город при следующем
сообщении. Если нужна постоянная привязка — вынесите этот словарь в файл
или БД.

## Логирование диалогов

Каждый вызов Claude (и промежуточные уточнения, и финальный ответ)
дописывается отдельной строкой в JSONL-файл (`AC_BOT_LOG_PATH`, по умолчанию
`dialogs.jsonl`) — один JSON-объект на строку: время, chat_id, город,
уличная температура, что написал клиент, накопленные уточнения и полный
разобранный ответ Claude. Формат удобно:

- смотреть в реальном времени: `tail -f dialogs.jsonl`
- построчно парсить скриптом на Python (`json.loads` на каждую строку)
- загрузить в pandas: `pandas.read_json("dialogs.jsonl", lines=True)`

Именно по этому логу удобно вручную сверять, насколько разумно Claude
классифицирует незнакомые модели, и по итогам донастраивать `system_prompt.py`.

## Что можно доработать дальше

- И `PENDING_CLARIFICATION`, и `CHAT_CITIES` сейчас в памяти процесса — для
  продакшена лучше вынести в Redis/SQLite, иначе при перезапуске бота
  теряются незавершённые уточнения и привязки городов.
- Добавить ежедневную подписку: раз в день сам присылать апдейт по ранее
  указанной модели (нужна база подписчиков + модель + город).
- Добавить триггер на резкую жару/мороз в прогнозе (Open-Meteo отдаёт и
  прогноз, не только текущую температуру — можно дёргать `daily` вместо
  `current`).
- Ротация/архивация лог-файла диалогов, если поток сообщений станет большим
  (сейчас просто дописывается в один файл без ограничения размера).
